Progetto Cargo Service | LINK AL PROGETTO

Requisiti

La compagnia ci chiede di realizzare un sistema software (denominato cargoservice) che:
  • sia in grado di ricevere la richiesta di caricare sul cargo un container di prodotto già registrato nel productservice. La richiesta viene rifiutata quando:
    • il peso del prodotto è valutato troppo elevato, poiché la nave può trasportare un carico massimo di MaxLoad>0 kg.
    • la stiva è già piena, ovvero i 4 slot sono già occupati.
    Se la richiesta viene accettata, il cargoservice associa uno slot al PID del prodotto e restituisce il nome dello slot riservato. Successivamente, attende che il container del prodotto venga consegnato alla ioport. Nel frattempo, altre richieste non vengono elaborate.
  • sia in grado di rilevare (tramite il sensore sonar) la presenza del container del prodotto presso la ioport.
  • sia in grado di garantire che il container del prodotto venga posizionato dal cargorobot all'interno dello slot riservato. Al termine del lavoro:
    • il cargorobot deve ritornare alla sua posizione HOME.
    • il cargoservice può elaborare un'altra richiesta di carico.
  • sia in grado di mostrare lo stato corrente della stiva tramite una web-gui aggiornata dinamicamente.
  • interrompa qualsiasi attività e accenda un led se il sensore sonar misura una distanza D > DFREE per almeno 3 secondi (probabile guasto del sonar). Il servizio riprende le sue attività non appena il sonar misura una distanza D <= DFREE.

Analisi dei Requisiti

Dalla lettura attenta del testo emergono le seguenti entità logiche e concetti fondamentali da chiarire:

  • Differential Drive Robot (cargorobot): Un oggetto fisico (attuatore di comandi) impiegato per il posizionamento e il carico dei container nei rispettivi slot riservati all'interno della stiva, muovendosi in avanti, all'indietro e ruotando su se stesso.
  • Stiva della nave (hold): Un'area piana rettangolare destinata all'alloggiamento dei container, provvista di una porta di Input/Output (IOPort) e strutturata per ospitare un massimo di 4 slot fissi per il posizionamento sequenziale o logico dei prodotti merci.
  • HOME: Rappresenta l'area e la posizione iniziale in cui il cargorobot si trova all'interno della stiva prima di iniziare la fase di trasporto, nonché la posizione finale obbligatoria in cui fermarsi al termine di ciascuna operazione di posizionamento riuscita.
  • Rappresentazione della Mappa: Per permettere gli spostamenti coordinati del robot, la mappa viene definita come una matrice di celle quadrate della larghezza di 1 unità robotica (lunghezza fisica del cargorobot). La singola cella deve consentire di distinguere la propria tipologia funzionale: 
    
public interface ICell {
    boolean isHome();
    boolean isIoPort();
    boolean isReservedSlot();
    boolean isFree();
}

public interface IMap {
    ICell getCell(int x, int y);
    int getHomeX();
    int getHomeY();
}
  • Richiesta di Carico (loadRequest): Il sistema richiede di definire un messaggio contenente le informazioni utili per il processo decisionale (peso del prodotto, capacità complessiva, PID). Poiché i requisiti impongono una risposta esplicita e il blocco dell'elaborazione di nuove richieste esterne durante la fase di attesa della merce alla IOPort, l'interazione viene modellata nativamente come una richiesta Qak bloccante: 
    
Request loadRequest : loadRequest(Weight, Capacity, PID)
Reply loadAccepted : loadAccepted(SlotName) for loadRequest
Reply loadRejected : loadRejected(Reason) for loadRequest
    Questo modello soddisfa appieno il vincolo di non elaborare altre richieste durante l'attesa della consegna del container del prodotto alla ioport, in quanto la natura della richiesta qak è intrinsecamente bloccante.
  • Sonar Adapter (sonar): Un'entità logica astratta come attore che funge da adapter per i campionamenti del sensore fisico o simulato. Riceve le misurazioni di prossimità sulla porta di ingresso della stiva ed elabora gli eventi utili a rilevare la presenza del container: 
    
QActor sonar context cargoservice {
    State detect {
        emit productDetected : productDetected(X)
    }
    Goto detect
}
  • Gestione Guasti (sonarDistance): Per consentire l'interruzione globale delle attività a causa di anomalie prolungate del sonar (distanza D > DFREE per più di 3 secondi), l'allarme viene descritto senza ricevitori espliciti ed è modellato sotto forma di evento asincrono di sistema: 
    
Event sonarDistance : sonarDistance(D)
  • Web GUI Service (guiservice): Un servizio adibito alla gestione dell'interfaccia di monitoraggio dinamica. Per raccogliere e sincronizzare le informazioni sullo stato della stiva e della posizione del robot, si introduce un attore delegato alle risposte di polling dati: 
    
QActor guiservice context cargoservice {
    State s0 initial {

    }
    Transition t0
        whenMsg getX -> handleGetX
}
